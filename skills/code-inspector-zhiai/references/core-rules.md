## 规则记录格式

每条专项或通用规则都应能映射到以下字段：

```text
rule_id: 稳定且唯一，例如 COR-BOUNDARY-001
applies_when: 适用条件和排除条件
inspect: 要观察的代码/配置事实
evidence: 可定位的证据形式
severity: 默认 P0-P3；结合实际影响调整
false_positive_guard: 何时不要报告
verify: 推荐的安全验证命令或测试
```

规则是检查提示，不是无条件重构指令。项目约定、版本和业务不变量优先于通用偏好。

## 正确性

- `COR-CONTRACT-001`：核对输入、输出、错误和状态转换是否符合需求、类型/schema 和调用方假设。
- `COR-BOUNDARY-001`：检查空值、空集合、边界数值、超时、重复请求、部分失败和重入。
- `COR-STATE-001`：检查状态初始化、更新顺序、缓存失效和失败后的恢复是否保持不变量。
- `COR-RESOURCE-001`：确认文件、连接、锁、临时对象、订阅和任务在成功与异常路径都能结束。

只有能指出违反的契约或可复现路径时才报告；“看起来不常见”不是证据。

## 安全与隐私

- `SEC-TAINT-001`：从请求、文件、消息、环境变量或用户输入到 SQL、HTML、命令、路径、模板和反序列化点追踪未验证数据。
- `SEC-AUTH-001`：核对认证、授权、租户隔离、对象级权限和默认拒绝；不要只检查是否存在登录中间件。
- `SEC-SECRET-001`：识别硬编码密钥、日志泄露、错误回显和不安全默认配置；报告位置但脱敏值。
- `SEC-DATA-001`：检查个人数据的收集、存储、传输、保留、加密和日志最小化。
- `SEC-DEP-001`：检查直接依赖、锁文件、来源、版本范围和已声明的审计命令；不要无依据断言某依赖“有漏洞”。

将可利用性、暴露面和影响纳入严重度；仅存在命名为 `password` 的变量不能单独证明是秘密。

## 可靠性

- `REL-ERROR-001`：错误必须被处理、转换或带上下文传播；禁止空 catch、静默返回成功和丢失原始错误。
- `REL-TIMEOUT-001`：外部网络、数据库、队列和子进程必须有可解释的超时和取消边界。
- `REL-RETRY-001`：重试应有上限、退避、幂等性和可观测性；不要对不可重试错误盲目重试。
- `REL-FALLBACK-001`：降级、熔断和部分成功路径不能绕过权限、数据校验或一致性约束。
- `REL-RESOURCE-001`：检查资源释放、连接池、文件句柄、监听器、任务和临时文件生命周期。

## 并发与一致性

- `CON-RACE-001`：识别共享可变状态、检查-使用间隙、重复消费和无序写入。
- `CON-CANCEL-001`：异步任务、goroutine、线程、future 和队列消费者必须有生命周期、取消和退出策略。
- `CON-TRANSACTION-001`：确认事务边界覆盖所有相关写入，并处理提交失败、重试和外部副作用。
- `CON-IDEMPOTENCY-001`：对 webhook、消息、支付、批处理和重试入口检查幂等键与重复请求处理。

没有并发或事务证据时标记为“不适用”，不要凭空要求加锁或开启事务。

## 契约与兼容性

- `API-SCHEMA-001`：检查 schema、序列化、默认值、枚举、错误码和向后兼容性。
- `API-CONSUMER-001`：从调用方反查字段使用、版本协商、分页和空值语义。
- `API-MIGRATION-001`：迁移必须考虑旧版本、回滚、锁时间、数据回填和双写/双读窗口。
- `API-CONFIG-001`：配置键、环境变量和 feature flag 的默认值、类型、秘密和变更兼容性必须明确。

## 性能与资源

- `PERF-COMPLEXITY-001`：识别输入规模增长时的复杂度退化、重复遍历和无界递归。
- `PERF-LOOP-001`：检查循环内可外提的不变计算、可按概率或短路优化的条件顺序、以及不必要的集合/类型来回转换；只在有规模或热点证据时报告。
- `PERF-CONCAT-001`：识别循环内反复字符串拼接（`+`/`+=`）或反复构造大对象；按语言建议 builder/join/StringIO 等聚合方式，小规模或常量拼接不报。语言专项规则（如 Go `GO-BUILDER-001`）引用本编号而非另立主编号。
- `PERF-IO-001`：识别循环内网络/数据库/磁盘 IO、N+1、重复序列化和不必要的全量读取。
- `PERF-BOUND-001`：检查分页、批量大小、缓存上限、并发度、请求体和队列积压是否有界。
- `PERF-MEASURE-001`：没有基准、执行计划或指标时，使用“可能”并给出验证办法，不把猜测写成事实。

## 测试

- `TEST-BEHAVIOR-001`：测试应验证用户可观察行为、错误和边界，而不是只覆盖行数。
- `TEST-ASSERT-001`：检查断言是否真实失败、是否只验证 truthy、是否误用 mock 绕过核心逻辑。
- `TEST-REGRESSION-001`：每个 P0/P1 行为缺陷都应有针对性回归测试或明确说明为何无法添加。
- `TEST-CONTRACT-001`：跨服务、schema、迁移和序列化变化应考虑契约/集成测试。

## 可维护性与运维

- `MAINT-BOUNDARY-001`：检查模块职责、依赖方向、公共接口和跨层泄漏。
- `MAINT-COMPLEXITY-001`：以认知负担和变更风险为依据处理过长函数和深嵌套，不以固定行数或参数个数机械扣分；重复代码见 `MAINT-DUP-001`，函数/文件长度、圈复杂度、嵌套和参数的固定阈值参考见门控的 [style-readability.md](style-readability.md)。
- `MAINT-DEAD-001`：识别注释掉的死代码、不可达分支、永假条件、遗留开关和未被引用的私有符号；确认无框架/反射/外部调用依赖后再建议删除，历史由版本控制承担。
- `MAINT-DUP-001`：识别可抽取的重复代码块、可合并的相似条件分支、多处重复定义的常量和无实际逻辑的包装函数；合并前确认差异是有意为之还是巧合相似。
- `MAINT-UNUSED-001`：检查未使用的 import/依赖、变量、函数、类型和参数；语言专项规则（如 `JS-DEP-001`）的未使用依赖结论引用本编号；注意导出符号、动态引用、反射、序列化和框架约定造成的假阳性。
- `MAINT-SIMPLICITY-001`：检查 DRY/KISS/YAGNI 违背与过度设计（为假设的未来提前抽象、不必要的配置层/接口层）；只在增加真实认知负担时报告，不把“看起来灵活”当缺陷。
- `MAINT-TESTABILITY-001`：检查难以测试的设计（隐式全局依赖、不可注入的外部客户端、直接内联的时间/随机/IO）；建议依赖注入、纯函数或端口抽象，但须结合项目既有架构。
- `OPS-LOG-001`：日志要有事件、关联 ID、级别和可操作上下文，且不泄露秘密/个人数据。
- `OPS-HEALTH-001`：服务应有合理健康检查、超时、指标和失败告警；不要把日志数量当成可观测性质量。
- `STYLE-CONFIG-001`：格式和惯用法默认低优先级，仅在项目没有相反配置且能降低维护成本时报告；需要成体系的风格/可读性/结构检查时，按门控条件加载 [style-readability.md](style-readability.md)。

## 误报控制

报告前逐项确认：代码路径确实可达；影响不是纯理论；规则适用于当前版本；项目配置没有明确允许该模式；问题不是生成代码或测试夹具中的有意行为。无法确认时降为 `low` 置信度并列入待确认项。
