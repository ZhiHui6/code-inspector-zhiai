## 报告结构

按以下顺序输出中文 Markdown 报告：

1. **范围与假设**：目标、模式、语言/版本、框架、文件统计、排除项。
2. **执行摘要**：P0-P3 数量、最高风险、主要未覆盖项和总体建议。
3. **验证状态**：已运行命令、退出码、关键结果；未运行命令及原因。
4. **问题清单**：按严重度排序，再按文件位置排序。
5. **专项覆盖**：加载了哪些规则包、哪些不适用、哪些语言/工具未识别。
6. **整改顺序**：最小修复、回归测试、后续重构和可选优化。

## 发现字段

每个发现使用全局递增的 `ISSUE-001` 编号，并填写：

```text
ISSUE-001: 简短标题
- rule_id: SEC-TAINT-001
- severity: P0 | P1 | P2 | P3
- confidence: high | medium | low
- location: absolute-or-repository-relative/path:line[:symbol]
- evidence: 最小必要的代码事实或脱敏片段
- impact: 可观察后果、受影响边界和触发条件
- recommendation: 最小可行修复方向
- verification: 测试、静态检查或人工复核步骤
```

一个模式在多个位置出现时可以归并，但必须列出所有受影响位置或明确代表范围。不要只写“代码质量不好”“存在潜在问题”等无法核验的结论。

## 修复输出

Review 和 Audit 不输出完整重写文件。用户明确进入 Fix 模式时：

- 使用 GitHub unified diff 或实际文件补丁，保留未涉及的用户改动。
- 只修改授权范围；不要顺便格式化整个仓库、更新锁文件或升级依赖。
- 修改位置用 diff 上下文和 `ISSUE-xxx` 关联，不把注释硬编码进生产代码。
- 行为变化必须给出测试变更；无法测试时说明原因和剩余风险。
- 修复后重新运行最小相关命令，并报告失败或跳过情况。

## 验证记录

记录命令、工作目录、工具版本（可获得时）、退出码和结果摘要。命令因缺依赖、超时、权限、网络或环境不确定而未运行时，写明原因，不声称“已通过”。

## 可选评分

默认不输出综合 A-F 分数，以免把不适用维度和样式问题混入发布判断。用户明确要求时才评分：

1. 仅对实际适用的核心维度计算，每个维度从 100 开始。
2. 采用固定扣分（P0/P1/P2/P3 = 30/15/5/1），同一根因在同一维度只扣一次。
3. 分数下限为 0，综合分为适用维度的加权平均，并公开权重和扣分表。
4. P0/P1 仍单独作为发布门槛，不能被高分抵消。
